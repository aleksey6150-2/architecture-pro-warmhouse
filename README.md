### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Необходим выезд специалиста, специалист ставит датчик и заводит его по sensorId в системе
- Пользователи могут  удаленно включать и выключать отопление
- Система поддерживает добавление, удаление, обновление новых датчиков, а также запрос их состояния

**Мониторинг температуры:**

- Пользователи могут просматривать температуру
- Система поддерживает просмотр температуры вместе со статусом датчика

### 2. Анализ архитектуры монолитного приложения

Язык программирования GoLang
База данных: Postgresql
Взамодействие между компонентами синхронное через rest-запросы
Для данного примитивного функционала система сколь угодно масштабируема - в том числе с шардингом БД по ключу от sensorId

### 3. Определение доменов и границы контекстов

Приложение на данный момент крайне примитивное, есть только CRUD методы по датчикам, установку значений и просмотру температуры

В текущем функционале нет ничего кроме домена: система прямого управления датчиками и реле

### **4. Проблемы монолитного решения**

Система в такой базовой реализации с таким функционалом хорошо масштабируется. Проблемы будут при добавлении нового функционала: управление пользователями (сейчас все пользователи могут делать что угодно кому угодно), устройствами (чтобы пользователь мог из заводить), асинхронные задачи (например управление контроллерами по расписанию, выключение отопления по достижению температуры). Тогда всплывут проблемы:
- невозможность масштабирования компонент
- единая точка отказа (особенно критично в части асинхронного управления)
- сложность в добавлении новых устройств
